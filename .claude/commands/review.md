# /review — 零推荐职位激活系统代码审查

审查当前分支或用户指定范围的代码变更，对照本项目权威文档、模块边界、安全与规范门禁，输出有证据的分级问题清单。审查是代码合并前的最后一道门禁（见 [开发与交付流程](../../docs/08-development-workflow.md) §2 第 9 步）。

## 1. 确定审查范围

优先使用用户指定的 commit、分支或目录范围。用户未指定时：

1. 仓库已有远端主分支：审查 `origin/main...HEAD`。
2. 仓库尚无远端或首个提交：审查暂存、未暂存和未跟踪文件。
3. 输出实际审查范围，不得假定命令执行成功。

## 2. 识别受影响模块

按路径分类：

| 路径 | 模块 |
|---|---|
| `apps/web/app/` | 页面与 React 组件（Vinext App Router） |
| `apps/web/lib/` | 业务模块：`jobs/`、`sources/`、`identity/`、`security/`、`server/`、`adapters/` |
| `apps/web/lib/adapters/` | 外部供应商适配器（MCP、LLM、短信、邮件） |
| `apps/web/scripts/` | CLI 任务（`run-under-served-sync`、`run-retention`、种子、MCP 采样） |
| `apps/web/worker/`、`apps/web/vite.config.ts` | Worker 运行时接线（Hyperdrive / env / DB 客户端） |
| `apps/web/db/` | Drizzle schema 与迁移 |
| `apps/web/tests/` | 单元与集成测试 |
| `docker-compose.yml`、`Makefile`、`Dockerfile`、`.env.example` | 部署与基础设施、环境契约 |
| `docs/`、`CHANGELOG.md`、`README.md` | 权威文档与交付记录 |

读取所有变更文件的完整上下文；不要只依赖 diff 片段。

## 3. 读取权威文档

所有审查必须读取：

- `CLAUDE.md`（开发原则、开发门禁、ADR 检查、完成声明）
- `docs/08-development-workflow.md`（RED/GREEN/REFACTOR 顺序与交付模板）

按变更范围增加：

| 变更 | 必读文档 |
|---|---|
| 项目目标、用户与范围 | `docs/00-project-charter.md` |
| 业务规则、流程与脱敏口径 | `docs/01-mvp-requirements.md` |
| 架构、模块边界、部署原则 | `docs/02-architecture.md`、相关 ADR |
| 数据模型、状态、保留 | `docs/03-data-model.md` |
| MCP 能力与接入规则 | `docs/04-mcp-integration.md` |
| 阶段与交付顺序 | `docs/05-roadmap.md` |
| 数据安全与触达门禁 | `docs/06-security-compliance.md` |
| 可执行验收条件 | `docs/07-acceptance-criteria.md` |
| 内部 API 契约 | `docs/09-api-contract.md` |
| 页面、交互与接线状态 | `apps/web/docs/FRONTEND.md` |
| 长期技术取舍 | `docs/decisions/ADR-NNN-*.md` |
| 已交付变更与验证状态 | `CHANGELOG.md` |

同一事实只在一份权威文档中完整定义；发现冲突时先修正文档，再修改测试与实现。文件尚未建立时应说明缺失；涉及相应设计的代码不得在无权威文档情况下被判定为完全通过。

## 4. 必查项

### 4.1 规范驱动 TDD 门禁

- [ ] 是否先确认唯一需求口径，再写代码？
- [ ] 是否做过 ADR 检查？命中长期绑定取舍时是否先建立并接受 ADR？
- [ ] 是否先写验收场景与接口契约，再写生产代码？
- [ ] 是否提供 RED 证据？RED 是否因目标行为缺失而失败（如缺失导出 `ERR_MODULE_NOT_FOUND`、断言失败），而非语法、Fixture、环境或 Mock 错误？
- [ ] GREEN 是否只包含通过当前测试所需的最小实现？
- [ ] REFACTOR 是否发生在测试全部通过之后，并保持外部行为不变？
- [ ] 是否执行了受影响模块的完整验证，而非复用旧测试结果？
- [ ] 纯文档、注释和不可执行配置是否符合例外条件，并执行适用的链接、格式、Schema 或配置检查？

以下情况标记为严重问题：无规范开发；生产行为先于测试；Bug 修复没有复现测试；测试从未正确失败；通过修改测试迎合错误实现；以手工测试代替自动回归测试。

### 4.2 模块边界与供应商隔离

- [ ] 业务模块是否直接依赖供应商原始字段或内部结构？
- [ ] MCP、LLM、短信、邮件和浏览器采集是否全部经 `lib/adapters/` 接入？
- [ ] 适配器是否在网络前拒绝非允许工具，并在字段类型漂移时阻止数据进入业务模型？
- [ ] 是否违反 MVP 边界，把机器人外呼、向量检索或自动推荐提前带入 MVP？
- [ ] 是否出现跨模块循环依赖或绕过适配器的直接调用？

违反供应商隔离或 MVP 边界标记为严重问题。

### 4.3 身份、权限与数据安全

- [ ] 口令是否 bcrypt 哈希（成本 ≥12）入库，会话令牌是否只保存哈希？
- [ ] RFC 6238 TOTP、连续失败锁定、首登强制改密是否符合规范？
- [ ] 业务端点是否用 `authorize` 服务端校验角色（`operations`/`recruiter`/`admin`）？仅隐藏前端按钮不视为通过。
- [ ] 审计日志是否追加写，`actor_type`/`action`/`result`/`request_id` 是否完整？元数据是否不含口令、令牌、手机号、邮箱、简历正文或完整载荷？
- [ ] 原始载荷是否 AES-256-GCM 信封加密入库，未以可读 JSON/明文存在？
- [ ] 真实密钥、真实联系方式、完整简历和可使用的落地页令牌是否未进入 Git、日志或测试夹具？
- [ ] 对外展示是否经过脱敏投影（隐藏公司名称、薪资只显示范围、地点只精确到城市）？
- [ ] 触达是否强制人工审核，不存在无审核自动群发路径？
- [ ] 是否存在硬编码密钥、Token、密码或本机敏感路径；SQL、路径、URL 是否有注入或越权风险？

权限泄漏、敏感信息外发、明文入库和注入风险标记为严重问题。

### 4.4 后端规范

- [ ] 仓储是否沿用原始 SQL 模式（函数接收 `sql` 客户端，postgres-js），未把 ORM 查询或供应商字段带进业务模块？
- [ ] `.mjs` 与 `.d.mts` 类型垫片是否成对维护？
- [ ] 同步/保留任务失败是否只记录机器可读 `error_code`，不落原始错误正文或凭证？
- [ ] 分页响应是否符合包络 `{ total, page, page_size, total_pages, list }`？
- [ ] Route Handler 是否只做会话校验、鉴权并调用仓储，未把 SQL 直接放进路由？
- [ ] 错误是否统一 JSON 契约，HTTP 状态是否语义正确？
- [ ] 时间是否统一使用数据库 `timestamptz`，客户端是否用 `new Date(isoString)` 转换？

### 4.5 MCP 契约专项

- [ ] 是否先修改契约再修改 Provider/Consumer？
- [ ] 字段字典、版本化输入契约与脱敏 Fixture 是否同步？
- [ ] 是否存在字段删除、改名或语义变化造成 Breaking Change？
- [ ] Provider 与 Consumer 测试是否同时更新？
- [ ] 新版本是否提供兼容或迁移路径？

### 4.6 同步与保留任务专项

- [ ] 同步是否支持分页/游标，重复同步是否幂等（`source_connection_id` + `external_id`）？
- [ ] 原始快照是否追加写不覆盖，规范化职位是否可追溯数据源、原始记录和映射版本？
- [ ] 分页截断、限流失败（如 `RATE_LIMITED`）是否归类错误码并标记？
- [ ] 保留任务 TTL 是否可配置，清理后是否写 `retention.run` 审计且不含敏感字段？
- [ ] 保留删除是否覆盖原始、规范化、审计和过期会话四类，并与数据模型保留口径一致？

### 4.7 前端专项

- [ ] 页面是否经 API 层取数，未直连数据库？
- [ ] 业务数据是否经脱敏投影（如 `toPublicJobView`）渲染，未泄漏公司名/详细地址/薪资精确值？
- [ ] 会话门禁是否符合分层（SSR Cookie 门禁 + 客户端 `me` 核实）？HttpOnly Cookie 下是否未用 `document.cookie` 判断登录态？
- [ ] 列表/详情是否有加载、错误、空态？状态标签是否映射成功/失败/运行中/排队中？
- [ ] 危险操作是否二次确认并正确恢复 loading？
- [ ] 新增颜色是否登记到 `:root` 设计 token，未在组件内硬编码色值？

### 4.8 测试质量

- [ ] 测试是否能明确指出哪项生产行为变化会使其失败？
- [ ] RED 与 GREEN 是否运行同一个目标测试，而不是中途更换断言？
- [ ] 成功、失败和关键分支是否成对覆盖（如 7 天边界、30 天边界、零推荐判定）？
- [ ] 是否存在弱断言或条件断言（如只断言非空、`>=0`）？
- [ ] 是否复制生产逻辑到测试？
- [ ] Mock 是否放在外部边界（如注入假 MCP callTool）并保留真实业务逻辑？
- [ ] 集成测试是否使用真实 PostgreSQL 大版本；共享 dev DB 下是否按夹具范围断言（旧删新留/下限），而非全局精确计数？
- [ ] 完成声明是否附有本次实际执行的测试命令、结果和已知偏差？

### 4.9 文档一致性

- [ ] 实现是否符合产品与架构规范（唯一权威来源）？
- [ ] 行为变化是否更新 `CHANGELOG.md`，状态标注是否为 `specified`/`implemented`/`verified` 之一？
- [ ] `verified` 声明是否附实际运行命令与结果，未把文档完成或代码存在描述为已验证？
- [ ] 重要决策是否新增或更新 ADR？
- [ ] 路线图与 FRONTEND 接线状态是否与代码一致？
- [ ] 同一技术事实是否在多个文档重复定义并产生漂移？

## 5. 输出格式

```markdown
## 审查报告 — [范围]

### 审查范围
- 变更文件：N
- 影响模块：...
- 对照文档：...
- 验证命令：...

### 严重问题（必须修复）
按 文件:行号 列出问题、证据、影响和建议。

### 规范问题（建议修复）
按 文件:行号 列出问题、证据、影响和建议。

### 改进建议（可选）
只列与本次变更直接相关的建议。

### 模块边界与安全
说明供应商隔离、身份权限、脱敏、加密、审计与触达门禁检查结果。

### 测试与验证
列出 RED 失败证据、GREEN 通过证据、完整验证命令、结果和未验证范围。

### 文档一致性
说明权威文档、CHANGELOG、ADR、TODO 和路线图状态。

### 通过项
列出经证据确认通过的关键检查项。
```

## 6. 审查原则

- 每条问题必须引用具体文件、行号和对应规则。
- 先检查规范/TDD 过程证据，再评价最终代码；最终有测试不代表遵循测试先行。
- 不把个人风格偏好当作缺陷。
- 不因测试存在就假定质量合格，必须检查断言和真实执行路径。
- 不因文档声称完成就假定代码完成，也不因代码存在就忽略文档缺失。
- 无法验证的内容明确标记为“未验证”，禁止推测通过。
- 代码与权威文档冲突时先报告，不自行修改设计迁就代码。
- 优先报告会导致越权、数据泄漏、脱敏失效、明文入库、审计缺失或供应商耦合的问题。
