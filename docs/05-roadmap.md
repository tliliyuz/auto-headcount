# 实施路线图

本文档是「零推荐职位激活系统」的权威实施计划，回答：按什么顺序交付、每个里程碑的进入/退出条件是什么、当前推进到哪一步、谁在阻塞。产品范围见 [项目章程](00-project-charter.md) 与 [MVP 需求](01-mvp-requirements.md)，验收条件见 [验收标准](07-acceptance-criteria.md)。

以下周期按一名主要开发者估算，外部接口、短信模板、部署审批延迟不计入开发时间。

## 1. 里程碑状态定义

| 状态 | 定义 |
|---|---|
| 未开始 | 进入条件尚未满足，或尚未投入实施 |
| 进行中 | 进入条件已满足，正在完成规范、实现或验收 |
| 受阻 | 存在明确阻塞条件，且已记录解除条件 |
| 已完成 | 本阶段全部退出门禁已有可复核证据 |

禁止用主观完成比例替代门禁结果。状态变化必须能在 [变更日志](../CHANGELOG.md) 中找到对应的实际验证记录。

## 2. 里程碑总览

| 里程碑 | 状态 | 名称 | 核心结果 | 主要依赖 |
|---|---|---|---|---|
| M0 | 进行中 | 接口与样本验证 | MCP/Web 接口清单、虚构化样本与已接受的身份/区域/数据生命周期方案 | 无 |
| M1 | 已完成 | 数据底座 | 可重复同步并查询沉睡职位与候选人的内部系统 | M0 |
| M2 | 进行中 | 数据获取与适配 | MCP/Web 数据经适配器进入统一、可追溯的内部数据模型 | M1 |
| M3 | 进行中 | 数据集成与匹配 | 从统一数据投影生成可审核的职位—候选人匹配池 | M1；真实数据验收依赖 M2 |
| M4 | 未开始 | 落地页与触达 | 从审核到候选人反馈的可运行闭环 | M3 |
| M5 | 未开始 | 漏斗与推荐 | 可演示、可度量、可验收的 MVP | M4 |

主线：`M0 → M1 → M2 → M3 → M4 → M5`。M2 与 M3 是两个连续编号的能力层，不再拆分 A/B/C 子阶段：M2 统一数据获取和供应商适配，M3 统一数据集成和匹配。M3 可使用完全虚构 Fixture 与 M2 并行开发，但真实数据集成验收必须等 M2 完成最小采集闭环。M1 已在 M0 技术门禁通过后按「最低权限开发假设」提前起建；真实数据上线仍以 M0 的书面授权门禁为准。

## M3：数据集成与匹配（进行中）

### 阶段目标

将统一职位、候选人与简历数据转换为展示摘要、过滤画像和详情匹配输入，形成可复算、可解释、可审核的匹配池。

### 进入条件

- [x] M1 已通过全部退出门禁（生产部署门禁已决策顺延）。
- [x] 虚构职位/候选人 Fixture 可在不依赖外部数据源的情况下验证匹配行为。

### 当前状态

已用完全虚构 Fixture 验证 `ADR-005` 两阶段主路径：不可变职位/候选人投影、残留 PII 拒绝、确定性硬过滤、符合 v1 Schema 的 Fake LLM 七维输出、`aggregation/v1` 本地汇总、版本束幂等、匹配追溯写入以及列表/详情/审核/异常 API。`match_pipeline_v2` 已接周期自动编排，并实现稳定预排序、每职位 Top-K 与单轮全局预算；MatchingPage 已接真实 API，职位页已移除人工创建入口。真实候选人输入和批准的生产 LLM 适配器仍未实现，PostgreSQL 整体闭环需在提供数据库的环境复验。

> **成本上界（2026-08-13，已实现默认机制）**：硬过滤通过者先做稳定本地预排序，再执行每职位 Top-K（默认 10）与单轮全局预算（默认 20）；预算外组合留待后续周期。真实通过量与费用数据到位后再校准默认值。

### 范围内工作

- 将统一数据契约映射到不可变 `job_match_projections` 和 `candidate_match_projections`，处理字段缺失、多源冲突和异常队列；现有 `job_requirements`/`candidate_profiles` 降为迁移期查询快照。

- 实现 LLM 适配器的脱敏详情维度评分，保存模型、Prompt、Schema、输入/输出哈希、证据、缺失项和风险版本。
