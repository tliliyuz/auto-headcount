# MVP 产品需求

## 1. 业务流程

### 1.1 职位巡检

1. 运营人员触发同步，或系统按计划执行同步。
2. 数据源适配器按来源调用 MCP，或向绑定设备下发版本化 Web 提取契约；业务模块不直接依赖供应方字段、DOM 或选择器。
3. 系统保存必要的加密原始快照、规范化字段并完成幂等去重；完整简历与联系方式不得经通用 Agent/MCP 结果传输。
4. 按职位类别、沉睡时长、负责人和状态提供列表与筛选。

授权 Web 职位采集采用两阶段固定工作流。猎必得列表不提供“发布 7～30 天”筛选，运营人员只负责人工登录/验证码，并完成“推荐 0 人、发布时间最近 30 天”筛选；随后在管理端点击“采集当前筛选结果”并选择本批数量。`batchSize` 采用差分口径：**本批数量 = 本次要处理的「新增 + 标题变化」职位数**。发现任务读取该来源已入库职位集合，跳过已入库且标题未变的职位，按合同 `nextPage`/`nextOffset` 数字断点向后翻页直到凑满本批数量或列表到底，再为「新增 + 标题变化」的职位创建 `browser_job_collect` 详情任务（标题变化由事务 upsert 覆盖，不产生重复职位）。生产任务不接受自然语言提示词、任意 URL、脚本或选择器。

列表筛选只负责缩小候选范围，不能作为入库证据。最近 30 天列表会包含发布 0～6 天的职位；每个详情任务必须做确定性导航，并重新确认页面职位 ID、`active`、发布 7～30 天和有效推荐数为 0。0～6 天及其他不合格项只记跳过，不写职位。批次、发现条目、断点、详情任务状态和有限重试由 auto-headcount 持久化管理，浏览器执行始终绑定明确的 `userId + deviceId`。MVP 单设备部署从服务端 Secret `BROWSER_RELAY_USER_ID`、`BROWSER_RELAY_DEVICE_ID` 注入该路由，运营页面不得要求重复填写，也不得允许请求体覆盖服务端绑定。

沉睡职位定义为：截至巡检时刻，发布已满 7 个自然日且不超过 30 个自然日、职位状态仍有效、有效推荐数为 0。边界 7 天和 30 天均包含在内。接口字段映射以对方 Schema 为准，但不得改变该业务口径。

**来源边界（2026-08-13）**：MCP 源只入库「账号可操作 ∩ 沉睡」（可操作 = `wb.jobs.list` 账号自身作用域，`match_candidates` 可用）；不在交集的上游仍沉睡职位标记 `operability_status=not_in_access_scope`（**非 closed**），不进入 MCP 可操作视图。根据 `ADR-005`，授权 Web 采集作为第二条正式数据源承接更宽的职位、候选人和简历范围；Web 记录仍必须独立证明 7～30 天、有效和零推荐，不得把“网页可见”直接等同于“沉睡”。

### 1.2 数据处理

- 职位和候选人分别保留必要的加密原始数据与规范化数据；字段记录来源、契约/映射版本和采集时间。
- 展示摘要不超过 150 个字符，并避免输出联系方式和直接身份标识。摘要只用于列表/审核概览，不是硬过滤或详情匹配的唯一输入。
- 职位和候选人都必须生成不可变的版本化匹配投影，保存 Schema/生成器/脱敏版本、来源快照引用、输入哈希和生成时间。职位投影包含展示摘要、硬要求和详情评分上下文；候选人投影包含展示摘要、结构化画像和脱敏简历详情。
- 完整 JD（`job_description`）落库 `jobs` 表，由 `wb.jobs.get` 独立同步补全（`job_details_jobs`，DB 驱动，只对可操作∩沉睡缺 JD 职位调用），仅管理端详情视图可见；落地页白名单投影始终禁止输出原始 JD。
- Web 采集使用 CSDN-Agent 浏览器执行端的版本化受限提取契约。Cookie、密码、验证码和原始 Authorization 始终留在员工浏览器；完整简历/联系方式使用短期单次 ingestion ticket 直接提交本系统，不经过 Agent 对话或通用 MCP 工具结果。
- 候选人联系方式单独加密保存；匹配模块只读取不含姓名和联系方式的评分投影。提交 Git/CI 的样本必须完全虚构化，不能只对真实简历做打码。
- 同一外部数据源、同一外部 ID 的重复同步执行更新而非新增。
- 缺少关键字段的数据进入异常队列，不直接参与触达。

### 1.3 候选人匹配

匹配采用「本地确定性硬过滤 + LLM 脱敏详情维度评分 + 本地固定权重汇总」的两阶段混合路径；供应方 `match_candidates` 结果仅保存为外部对照。详细字段与版本见 [匹配契约](10-matching-contracts.md)。

1. 第一阶段硬过滤：本地按工作地点、必备技能、最低工作年限、学历/证书和明确薪资边界判定；保存通过/剔除原因。不通过者不调用 LLM。
2. 第二阶段详情评分：LLM 适配器只读取职位要求投影和通过残留 PII 扫描的候选人脱敏简历投影，输出技能、行业、职级、经历、地点、薪资和活跃度维度分、证据、缺失项、风险和置信度。
3. 本地汇总：系统按版本化固定权重汇总已持久化的 LLM 维度结果，计算总分和分档。LLM 不直接输出总分、审核结论或触达决策。

正常匹配任务由系统自动编排，不再由运营人员勾选职位创建。职位/候选人投影、硬过滤规则、LLM 适配器/模型、Prompt、Schema 或汇总规则任一版本变化时，系统只消费受影响且通过硬过滤的组合；完全相同的版本组合不得重复调用 LLM。周期调度仅用于发现待消费版本与恢复可重试失败，不得每轮对全部职位盲目重算。运营人员只查看待审核结果和异常，审核通过/拒绝；异常重试只允许针对失败运行，不得借重试接口创建任意正常匹配任务。

为控制外部调用成本，自动编排必须同时设置单职位候选池上限和单轮全局预算，并在调用前做稳定的本地预排序。开发与 CI 使用实现相同评分端口的确定性 Fake LLM；生产环境未显式配置已批准的真实适配器时失败关闭，不得使用 Fake 输出充当生产分数。没有可消费投影时本轮成功空跑，不得临时捏造候选人、手机号、简历或评分输入。

默认等级：

- 高匹配：85～100。
- 中匹配：75～84。
- 低匹配：0～74，默认不进入触达候选池。

每个结果必须保存：职位/候选人投影版本与哈希、硬过滤规则及原因、LLM 适配器/模型标识及可得的模型修订、Prompt 版本、JSON Schema 版本、请求/输出哈希、维度分与证据、缺失项、风险、汇总规则版本、总分、分档和生成时间。禁止只保存一段无法复核的 LLM 文字结论。

可复核不等于重新调用 LLM 必然得到逐分一致结果。对同一份已保存的结构化 LLM 输出和同一汇总规则，重算必须得到相同总分和分档。模型、Prompt、Schema、投影或汇总规则变更时必须新建运行，不覆盖旧结果。

LLM 超时、限流和临时不可用可有限重试；输出 Schema 无效、脱敏失败、输入超限或安全策略拒绝时失败关闭。未成功得到合法维度输出时不伪造最终分、不回退供应商分数且不自动触达。

本地开发与 CI 使用完全虚构、确定性的职位/候选人 Fixture 跑通闭环；真实 MCP/Web 数据只用于有界集成验证，外部服务不可用不得阻塞业务测试。

### 1.4 人工审核

触达前，运营人员可以：

- 通过或拒绝匹配结果。
- 调整优先级并填写审核备注。
- 排除已拒绝、已退订或近期已被频繁联系的人选。
- 预览候选人看到的脱敏页面和文案。

### 1.5 落地页与意向

候选人通过一次性或可撤销的随机令牌访问页面，不能通过连续 ID 枚举数据。页面只展示经过白名单生成的脱敏职位信息：

- 隐藏公司名称、简称和可直接反推出公司的标识；
- 薪资仅展示上下限范围，不展示内部预算或精确个人定薪；
- 工作地点只精确到城市，不展示行政区、街道、楼宇或详细地址；
- 页面不得包含招聘负责人、客户联系人和内部职位编号。

页面提供：

- A：有兴趣，请联系我。
- B：暂不考虑。
- C：愿意了解更多/开放查看。
- 退订或不再联系。

提交操作需要防重复和防机器人滥用。联系方式原则上来自已授权数据；如需重新收集，应明确用途并征得同意。

### 1.6 触达与漏斗

事件主链路：

```text
message_queued → message_sent → message_delivered/failed
→ link_clicked → page_viewed → intent_selected
→ contact_confirmed → recommended
```

所有事件至少包含活动、职位、候选人、渠道、时间和可追踪关联 ID。看板需展示按职位、类别、活动、时间和渠道的转化情况。

### 1.7 推荐闭环

- 对“有兴趣”人选建立人工跟进任务。
- 记录联系结果、确认意向和推荐状态。
- 通过 MCP 推荐接口或 Portal 完成正式推荐。
- 保存外部推荐 ID、执行人、时间和结果，避免重复推荐。

## 2. 非功能需求

- 外部调用必须设置超时、有限重试、幂等键和审计日志。
- Web 采集默认单并发并受页面/小时/日预算限制；浏览器离线、登录失效、验证码、429、异常跳转或页面契约变化时失败关闭并可暂停数据源。
- 所有管理端页面必须登录并按角色授权。
- 敏感字段加密存储，日志默认脱敏。
- 关键操作可追踪到操作者和请求关联 ID。
- MVP 目标支持 100 个职位、5,000 个候选人和一次 5,000 人以内的活动；实际容量需压测确认。
- 数据导出必须受权限控制并记录审计事件。

### 2.1 管理端身份与角色

- 管理端不开放自主注册；用户由管理员邀请/启用，使用自有账号口令登录（`ADR-004`）。
- `operations` 可执行职位巡检与同步、查看自动匹配结果、审核/处理匹配异常和准备活动草稿；不得人工创建正常匹配任务。
- `recruiter` 可审核获授权候选人、处理跟进并登记推荐结果。
- `admin` 可管理用户角色、连接元数据、系统开关、审计和保留任务，但任何角色都不得读取 Secret 明文。
- 权限必须由服务端校验；前端隐藏入口不能作为授权措施。
- 数据导出、批量触达批准、正式推荐、角色变更和数据删除必须独立授权并记录审计。
- 活动创建人与批准人不得为同一人；无法满足职责分离时，真实批量触达保持关闭。

#### 登录方案（2026-08-12 确认）

- 认证方式：账号 + 口令（自有登录，`ADR-004`），登录成功后建立服务端会话。
- 口令存储：argon2id 或 bcrypt 哈希，不保存明文口令；口令与口令哈希不得进入日志、审计或错误上报。
- 口令策略：最小 12 位且包含字母与数字，拒绝常见弱口令；口令或 TOTP 校验失败均计入连续失败锁定（阈值如 5 次）并限流，锁定期满自动恢复。
- 会话：浏览器保存 `HttpOnly`、`Secure`、`SameSite=Lax` 会话 Cookie；空闲 30 分钟失效、最长 12 小时；管理端写操作执行 CSRF 防护；用户禁用或角色变更后现有会话必须可撤销。
- 首个管理员：生产首次部署由初始化脚本创建（一次性凭证，首次登录强制改密），脚本同时生成 TOTP 共享密钥并输出配置 URI，操作者录入认证器后首登即使用「口令 + 动态码」；开发环境使用仅 `development` 编译启用的 Fixture 登录，测试与生产启动时拒绝该路径。
- 密码重置：由 `admin` 手动重置并强制该用户首次登录改密；MVP 不接邮件/短信自助找回。
- 多因素认证：生产环境管理员账号强制绑定并校验 TOTP，绑定在初始化脚本预置密钥时完成（登录时校验动态码）；开发与测试不强制。
- 账号生命周期：管理员邀请/启用/禁用/删除用户；被禁用账号的已有会话立即失效。

本节身份部分为 `ADR-004` 的产品投影，角色与权限沿用 `ADR-003`；真实数据上线仍需满足数据授权与最终保留期限门禁。

## 3. 待产品确认

- Web 自动化采集的最终供应方条款确认、允许字段/频率、完整简历与联系方式的保存期限和删除要求；当前负责人已确认可用已开通账号做受控采集，更严格要求到达后从严。
- 供应方 `match_candidates` 的评分费用与超时口径（只影响外部对照，不阻塞本地匹配）。
- 两阶段匹配的具体 LLM 供应商/模型、中国大陆处理区域、数据不用于训练条款、费用预算和超时上限；未确认前真实 LLM 调用保持关闭。
- A/B/C 的最终中文文案和 C 选项业务含义。
- 触达前是否必须逐条人工审核。
- 正式推荐的接口、状态回写和失败补偿流程。
- 自有账号口令策略（哈希算法、复杂度、限流锁定）与管理员多因素认证能力。
- 中国大陆测试/生产区域、云厂商、域名备案及跨境服务清单。
- 各类候选人数据、原始载荷、审计与备份的最终保存期限和删除例外。
