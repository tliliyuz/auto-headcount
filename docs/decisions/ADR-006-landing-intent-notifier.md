# ADR-006：落地页意向反馈实时通知（飞书）

- 状态：accepted
- 日期：2026-08-14
- 修订：2026-08-14（项目负责人确认，proposed → accepted）
- 决策人：项目负责人
- 替代：无；扩展 [`ADR-005`](ADR-005-authorized-web-collection-and-local-matching.md) 的触达边界

## 背景

M4 落地页的目标是「从审核到候选人反馈的可运行闭环」：候选人在脱敏落地页表达 A/B/C 意向并提交联系方式，运营需要**实时**跟进，而不是等回查列表。当前系统只有管理后台的异步列表/审计，没有实时触达渠道；意向数据只躺在库里，运营跟进存在滞后，转化闭环不完整。

候选人在落地页**主动提交**联系方式表达意向，这就是「同意被联系」的授权基础。把这条意向实时推给运营需要一个内部即时通讯渠道：候选人群体的短信/邮件渠道用于正式触达，不用于运营内部通知；飞书机器人 webhook 是团队现成可用、成本最低的即时通知通道（路线图 2026-08-14 决策先做飞书）。

这里的关键风险：**联系方式明文出库到第三方机器人 webhook**。手机号/邮箱属于高敏感数据（[`docs/06-security-compliance.md`](../06-security-compliance.md) §2 数据分类），飞书虽是境内平台、不构成跨境，但仍是一次对第三方的数据流出，必须明确数据流、必要性、最小化、授权边界和审计，否则违反 06 §4.2「向第三方 SaaS 发送候选人个人信息默认禁止；启用前必须完成数据流、必要性评估」与 [路线图 M4](../05-roadmap.md)「动工前需先立 ADR 与授权范围」。

## 决策

### 1. 意向是真源，通知是尽力转发的投影

- 落地页意向与联系方式的持久化**真源**是 PostgreSQL（意向事件表，联系方式应用层加密）。飞书通知只是「尽力转发」的投递，不承载业务状态：通知失败不得回滚意向落库，意向必须始终可查、可复核。
- 通知触发条件：意向事件成功落库后异步投递；投递失败记录审计与可重试标记，不伪造「已通知」。

### 2. notifier 适配器接口，第一实现是飞书 webhook

- 新增 `notifier` 适配器接口（发送渠道可替换，企微等作为扩展点），业务模块不依赖飞书原始字段。
- 第一实现为飞书群机器人：向内部运营群 webhook POST JSON。webhook URL 与签名 secret 只从部署密钥服务（环境变量/密钥文件，gitignored）读取，**禁止进入 Git、日志、审计元数据或前端**。

### 3. 最小化 payload

飞书消息只携带跟进所需最小信息：

- 联系方式（手机号或邮箱，候选人主动提交的字段）；
- 意向选项（A/B/C 或退订）；
- 职位标识（可读标题 + 内部职位 id 便于后台定位；不含公司名称/简称/内部职位编号/详细地址）；
- 意向提交时间。

不发送：完整 JD、简历、公司名称、招聘负责人、客户联系人、原始页面令牌、候选人后台敏感画像字段。

### 4. 授权边界

- 只有候选人在落地页**主动提交**意向与联系方式才触发通知；仅打开页面、后台浏览不产生通知。
- 通知只发到运营内部群；接收者即内部运营角色，与后台 RBAC 的 `operations|admin` 同界。
- 退订选项同样触发通知（运营需要停止跟进/标记退订），payload 标注意向为退订。

### 5. 幂等与审计

- 幂等键 `(candidate_id, job_id, intent_event_id)`：同一意向事件只通知一次，重试不重复推送。
- 触发、成功、失败均写 `audit_logs`（action 白名单，如 `landing.intent.notify`）；审计元数据只含事件 id/幂等键/机器错误码，**不含联系方式正文**。
- webhook 返回非 2xx 或超时 → 记录失败 + 可重试标记；连续失败进入降级（见后果）。

### 6. 渠道与区域

- 飞书为境内平台，不构成数据出境；但按 06 §4.2 仍做必要性评估并记录于此：payload 最小化 + 境内 + 候选人主动提交同意，满足必要性。
- 若后续渠道切换或新增企微、邮件或境外 SaaS，必须先重新评估（见「重新评估触发条件」）。

### 7. 交付切片与后续

- 首个交付点：意向事件表 + 令牌门禁 + 脱敏职位页 + 意向提交 + 飞书通知，全链路用真实职位 + 完全虚构候选人 Fixture 验证（照 M2/M3 并行口径，见 [路线图](../05-roadmap.md)）。
- 真实候选人的批量触达仍受 M4 完整门禁（[`01`](../01-mvp-requirements.md) §1.5/§1.6、[`07`](../07-acceptance-criteria.md) §3、06 §5）约束；本 ADR 只放行「意向反馈通知」这一条数据流。

## 备选方案

- **不做实时通知，运营定时回查意向列表**：无第三方数据流、实现最简单，但跟进滞后，意向转化闭环不完整，不符合 M4「可运行闭环」目标。
- **短信/邮件通知运营**：走候选人群体的短信/邮件渠道，成本高、需要渠道账号与模板审批，且用短信做运营内部通知语义错配。不选择。
- **邮件通知**：境内邮箱可用，但即时性低于 IM，且同样需要渠道账号；留作 notifier 接口的后续实现，不作为首发。
- **企微机器人**：同为境内 IM，与飞书二选一即可；本轮选飞书（当前运营沟通主渠道），notifier 接口保证企微可低成本替换/新增。

## 后果

- **收益**：意向反馈实时到达运营，缩短「候选人有兴趣 → 运营跟进」的耗时，闭环可演示。
- **成本/风险**：联系方式进入飞书群聊消息，存在群内留存、转发、截图风险。缓解：payload 最小化、仅内部运营群、webhook 与签名 secret 轮换、通知即弃（不主动在飞书归档候选人数据）、意向真源始终在内部库。
- **审计**：触发/成功/失败全审计，联系方式正文不进审计。
- **运维面**：新增一个外部 webhook 依赖；失败降级 = 意向照常落库 + 审计记录失败 + 后台意向列表可见，通知恢复后重试（幂等键保证不重复）。
- **迁移/回滚**：notifier 接口隔离，关闭环境变量即停用通知，不影响意向落库与落地页访问；回滚只影响运营的实时跟进体验。
- 本 ADR 只确认规范（`specified`）；意向事件表、令牌门禁、脱敏页与飞书通知均未实现，不得声明该数据流可用。

## 重新评估触发条件

- 通知渠道变更（新增/切换企微、邮件、境外 SaaS）或通知 payload 扩大。
- 候选人联系方式的授权、保留或删除规则变化。
- 飞书数据处理条款变化，或出现跨境合规评估要求。
- 落地页从「脱敏公开面」变成需要登录/实名，或承载更多候选人画像字段。
- 运营通知内容开始包含简历、完整 JD 或其他高敏感字段。
